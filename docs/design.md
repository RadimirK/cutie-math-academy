# Cutie Math Academy — проектный документ v2

> Бывшее рабочее название: «Демидович-гача». Документ — единственный источник правды
> по правилам проекта: изменение инварианта сначала вносится сюда.

## Концепция

Веб-игра для небольшой компании друзей-студентов: аниме-гача, где валюта для круток
зарабатывается решением задач по предметам первого курса. Реальных денег и монетизации нет.
Теорию объясняют героини в сценах визуальной новеллы, а задачи генерируются из
параметрических шаблонов.

Сюжетный блок (теория) открывает доступ к пулу задач, заданных для этой теории.

Предметы: математический анализ (первый), линейная алгебра, дискретная математика,
алгоритмы и структуры данных. Архитектура с первого дня строится так, чтобы новый предмет,
тема или тип задачи добавлялся контентом и плагинами, без правок ядра.

Принципы:

- **Учёба не блокируется удачей.** Базовая теория и задачи любой темы доступны через
  прогрессию, а не через крутки. Гача даёт персонажей, бонусные сцены, сложные задачи и косметику.
- **Контент живёт в репозитории (YAML)** и версионируется вместе с кодом. Репозиторий является
  единственным источником правды, БД получает из него копию служебных данных.
- **Система на честном слове, но без дыр.** Проверка ответов идёт на клиенте, и факт решения
  можно подделать. Но размер наград, списание валюты, RNG и pity живут только на сервере.
- **Хостинг бесплатный:** статика на GitHub Pages, данные в Supabase.

## Инварианты

Эти правила обязательны для любой реализации. Изменение правила сначала вносится в этот документ.

1. Валюта, pity-счётчики, коллекция персонажей и симпатия меняются только через RPC-функции
   с `security definer`. Прямой UPDATE этих полей с клиента запрещён политиками RLS.
2. Размер награды, шансы и состав баннеров сервер берёт из своих таблиц, а не из запроса клиента.
3. Задача выдаётся сервером (`issue_problem`), награда за одну выданную задачу начисляется
   не более одного раза.
4. Id контента (предметов, тем, шаблонов, сцен, персонажей, баннеров) неизменяемы.
   Смысловое изменение шаблона означает новый id или новую `version`.
5. Каждый шаблон задачи проходит самотест в CI: эталонный ответ принимается собственным
   проверяющим на 20 разных seed.
6. Все YAML-файлы контента проходят валидацию схемой, все ссылки (goto, unlocks, character,
   topic) указывают на существующие объекты.
7. Ядро не знает о конкретных предметах. Всё предметно-специфичное находится в контенте и
   в плагинах типов ответов.
8. `service_role`-ключ Supabase никогда не попадает в репозиторий и в клиентский бандл.

## Решения по открытым вопросам

- **Название:** Cutie Math Academy.
- **Арт:** проект только для пары человек и распространяться не будет, поэтому допустимы
  чужие арты. Репозиторий при этом публичный (GitHub Pages), так что в `content/assets/`
  стоит класть файлы с указанием источника в `content/assets/CREDITS.md`.
- **Баннеры:** по одному на предмет, без ротации по времени.
- **Язык задач на код:** только Python.

## Игровые механики

Игровой цикл: игрок входит в тему → основная героиня темы выдаётся бесплатно и объясняет
теорию в VN-сцене → открывается блок задач → за решения начисляется валюта → за валюту
делаются крутки → выпавшие персонажи открывают бонусные сцены и сложные задачи.

**Предметы и темы.** Иерархия: предмет → тема → сцены и шаблоны задач. У темы есть список
тем-предпосылок (`requires`). Тема открывается, когда пройдены основные сцены тем-предпосылок.
Экран «карта предмета» показывает граф тем и прогресс по каждой.

**Персонажи.** Редкость 3★, 4★, 5★. Каждая героиня привязана к теме или к предмету. У каждой
темы есть основная героиня (выдаётся при входе в тему, её ветка является базовым курсом темы).
Остальные героини добываются гачей и дают бонусные сцены, «личные» сложные задачи и
альтернативные объяснения.

**Визуальная новелла.** Фон, спрайт с эмоциями, текстовое окно с KaTeX прямо в репликах,
доска с рисунками (диаграммы, графы, графики; некоторые интерактивные).
Внутри сцены бывают вопросы с вариантами. Неправильный выбор ведёт в ветку, где героиня
объясняет иначе, а не просто пишет «неверно». Прогресс сохраняется по узлам сцены.

**Задачи.** Генерируются из шаблонов по seed, пул бесконечный. Тип ответа задаётся плагином.

**Гача.** Баннеры привязаны к предмету. Шансы по редкости фиксированы и хранятся в БД.
Pity-система с гарантией 5★ и отдельной гарантией 4★. Одиночная крутка и x10 одним вызовом.

**Симпатия (affection).** Растёт при решении задач по теме героини. На порогах открываются
бонусные сцены, «личные» задачи и интерактивные действия с героиней.

**Социальное.** Общий лидерборд (по сумме сложности решённых задач) и лента событий.
Позже: еженедельный «рейд» (одна сложная задача на всех, награда первому).

## Экономика

Стартовые значения хранятся в `content/economy.yaml`, синхронизируются в БД.

| Параметр | Стартовое значение |
|---|---|
| Цена одной крутки | 160 |
| Награда за задачу | от 80 (сложность 1) до 1600 (сложность 5) |
| Затухание награды | 100% за первые 5 решений шаблона, затем 50%, после 15 решений 10% |
| Дневной лимит | валюта с шаблонов сложности 1–2 ограничена 10 крутками (1600) в сутки |
| Pity 5★ | гарантия на 70-й крутке |
| Pity 4★ | гарантия каждые 10 круток |
| Дубликат | +1 к созвездию до C6, дальше конвертация в валюту |

Затухание считается по `template_id` и не зависит от seed. Задачи со звёздочкой и рейды
затуханию не подлежат.

Все движения валюты пишутся в журнал `currency_ledger`. Баланс в `profiles` является кэшем
суммы журнала.

## Архитектура

```
[Браузер — GitHub Pages]
 ├─ src/core/             ядро, не знает о предметах
 │   ├─ VN-движок         сценарий → фон/спрайт/реплики/выборы/доска, сохранение узла
 │   ├─ Экран задачи      issue_problem → генерация по seed → ввод → проверка → submit_solution
 │   ├─ Гача              баннеры, pull(banner, count), анимация
 │   └─ Карта предмета, коллекция, профиль, лидерборд, лента
 ├─ src/answer-types/     плагины типов ответов (ввод + проверка)
 ├─ src/figures/          плагины рисунков (SVG)
 ├─ Web Worker            Pyodide + sympy: генераторы и проверяющие (python/cutemath)
 └─ content/              YAML, валидируется zod и собирается в бандл

[Supabase]
 ├─ Auth                  email + пароль, инвайт-коды
 ├─ Postgres + RLS        состояние игроков + копия служебного контента
 └─ RPC                   issue_problem, submit_solution, pull, complete_scene, redeem_invite

[GitHub Actions]
 ├─ ci: валидация контента, самотесты шаблонов, тесты
 ├─ sync-content: контент → upsert в служебные таблицы Supabase
 ├─ deploy: сборка и публикация на Pages
 └─ keepalive: cron-запрос к Supabase
```

Поток решения задачи:

1. Клиент вызывает `issue_problem(template_id)`. Сервер создаёт строку в `issued_problems`
   со случайным seed и возвращает её id и seed.
2. По шаблону и seed детерминированно строятся условие и эталонный ответ (декларативные
   шаблоны — в TS, шаблоны с генератором — в Python-воркере).
3. Игрок вводит ответ, плагин типа ответа проверяет его (при необходимости в воркере).
4. При верном ответе клиент вызывает `submit_solution(issued_id)`.

Неверный ответ не отправляется. Ошибка разбора показывается как «не удалось распознать ответ».

## Контент

```
content/
  economy.yaml
  subjects/<subject>/
    subject.yaml
    topics/<topic>/
      topic.yaml
      scenes/*.yaml
      problems/*.yaml
      generators/*.py
  characters/*.yaml
  banners/*.yaml
  art/parts/<slot>/*.yaml   # детали генератора портретов, см. docs/character-art.md
  assets/
```

**Id.** Полный id строится из пути: `calculus.seq_limits.lim_exp_1`. Внутри файла пишется
только локальная часть. Персонажи и баннеры имеют глобальные id. Сцены адресуются как
`<subject>.<topic>.<scene>`; внутри своей темы на сцену и шаблон можно ссылаться локальным id.

**Подстановки.** Параметры подставляются как `<<a>>`. Формулы пишутся в блочных скалярах `|`
или в одинарных кавычках.

**Детерминизм.** Декларативные шаблоны инстанцируются только в TS (`src/core/generate.ts`):
параметры берутся из PRNG `splitmix32(seed)` в порядке объявления, алгоритм закреплён
golden-тестом. Генераторы выполняются только в Python и получают `random.Random(seed)`.
Если проверка переедет на сервер, TS-инстанцирование придётся повторить в Python.

Примеры форматов файлов — в `content/` (живые) и в истории этого документа.

## Задачи: типы ответов

```ts
interface AnswerType<Cfg, Ans> {
  id: string;
  configSchema: z.ZodType<Cfg>;
  Input: React.FC<{ cfg: Cfg; onChange(a: Ans): void }>;
  serialize(a: Ans): string;
  check: "python" | ((user: Ans, correct: Ans, cfg: Cfg) => CheckResult);
}
type CheckResult = { ok: true } | { ok: false } | { parseError: string };
```

| Тип | Ввод | Проверка | Где нужен |
|---|---|---|---|
| expression | MathLive | численно в случайных точках, затем simplify | анализ |
| number | MathLive | точное сравнение, ±∞, «не существует» | все |
| choice, multi_choice | кнопки; верный ответ + выборка из пула неверных | совпадение | все |
| matrix, vector | сетка ячеек | поэлементно через sympy | линал |
| subspace | набор векторов | равенство линейных оболочек через ранг | линал |
| set | список элементов | равенство множеств | дискретка |
| logic | формула | эквивалентность | дискретка |
| sequence | список значений | поэлементно | алгоритмы |
| code | редактор кода | Python-решение на тестах в воркере | алгоритмы |
| custom | любой | `check(answer, params)` из шаблона | «приведите пример» |

В MVP: expression, number, choice, matrix.

У плагина может быть `prepare` — доводка config экземпляра по seed после генерации (choice
выбирает `count - 1` неверных вариантов из `distractors` и перемешивает их с верным).

У плагина может быть `quickCheck` — быстрый путь в TS для простых случаев (у number это
рациональные числа, ±∞ и «не существует»), чтобы такие ответы не ждали загрузки Pyodide.
Там, где быстрый путь даёт ответ, он обязан совпадать с Python-проверкой; самотест это сверяет.

Ввод: MathLive → LaTeX → Compute Engine (MathJSON) → `src/answer-types/mathjson.ts` → строка
sympy. Десятичная запятая (`3,5`) понимается как точка. MathLive и Compute Engine грузятся
отдельным чанком только на экране задачи, Pyodide и sympy — с CDN jsdelivr в Web Worker
(`src/worker/`), версия закреплена в `src/worker/config.ts`.

Ответы на границах модулей — строки в синтаксисе sympy (`exp(2*x)`, `3/4`, `oo`, `DNE`,
`[[1, 2], [3, 4]]`): Input сериализует, проверяющий разбирает.

**Проверка выражений.** MathJSON → собственный конвертер → строка sympy (LaTeX-парсер sympy
не используется). Основной арбитр — численная проверка в 8 случайных вещественных точках
(положительных и отрицательных) с относительным допуском 1e-9; точки, где хотя бы одна сторона
не определена или не вещественна, отбрасываются. `simplify` над ℂ отвергает верные на
вещественной области ответы (`ln(x²)/2 = ln x`), поэтому символьная проверка
(`simplify(user - correct) == 0`, таймаут 3 с) запускается, только если валидных точек меньше 3;
по таймауту ответ не засчитывается. Зависший воркер убивается через `terminate()`.

**Безопасность.** custom-проверяющие и генераторы допускаются только из репозитория после ревью.

## Рисунки

Рисунок — `{type, ...props}`, его тип задаётся плагином в `src/figures/` (схема props в `core.ts`,
SVG-вид в `Figure.tsx`), так же как типы ответов: ядро о конкретных рисунках не знает.
Типы: `venn`, `relation`, `cube`, `sequence`. Рисунок бывает у задачи (поле шаблона с подстановками
или результат генератора) и у реплики сцены: он остаётся на доске до конца узла, `figure: null`
стирает доску. С узлом доска начинается пустой, поэтому продолжение сцены с сохранённого узла
показывает ту же картинку. Рисунки сцен проверяет валидация, рисунки задач — самотест на каждом seed.
Рисунок в задаче не должен подсказывать ответ (интерактивный ползунок графика — только для сцен).

## Модель данных и RPC

См. `supabase/migrations/`. Таблицы состояния игроков пишутся только RPC-функциями,
служебный контент — только workflow синхронизации. Блокировка строки профиля в `pull` и
`submit_solution` обязательна.

## Авторизация

Email + пароль, регистрация только по инвайт-коду, подтверждение почты отключено.
Порядок: `signUp` → `redeem_invite(code, nickname)`. Без погашенного инвайта RPC игры отказывают.

Модель угроз: подделать факт решения можно (принято), подделать награду, крутку, pity — нельзя.
Эталонные ответы видны в бандле (принято).

## CI и синхронизация

| Workflow | Когда | Что делает |
|---|---|---|
| ci | каждый PR и push | zod-валидация YAML, проверка ссылок и ацикличности графа тем, самотест шаблонов, тесты |
| sync-content | push в main после ci | upsert служебных таблиц через service_role |
| deploy | после sync-content | vite build и публикация на Pages |
| keepalive | cron раз в 3 дня | лёгкий запрос к Supabase |

Контент в БД только добавляется и обновляется; удалённое помечается `retired = true`.

## План реализации

1. **Этап 0, каркас.** Vite + React + TS, HashRouter, деплой на Pages, Supabase, миграции,
   RLS, workflow ci, sync-content, deploy, keepalive.
2. **Этап 1, MVP.** Регистрация по инвайту; анализ: «пределы последовательностей», Коши,
   2–3 сцены, 5–10 шаблонов; линал: «определители», 2–3 шаблона на генераторах; типы
   expression, number, choice, matrix; Pyodide-воркер; валюта с журналом и затуханием,
   один баннер, x1/x10, pity, коллекция; карта предмета, прогресс сцен и тем.
3. **Этап 2, расширение.** Новые темы и типы ответов, симпатия, лидерборд, лента.
4. **Этап 3.** Алгоритмы (sequence, code), рейды, задачи от друзей, арт, вход через GitHub.

Критерий готовности этапа 1: новый шаблон задачи добавляется одним YAML-файлом и проходит CI,
новая тема добавляется одной папкой, и в обоих случаях код не меняется.
